# Event Model

## Purpose

The Event Model defines how changes propagate throughout the Cosmos Runtime.

Events allow Runtime components to react to completed actions without creating direct dependencies.

Events communicate what has happened.

They never request work.

---

# Philosophy

Commands request work.

Services perform work.

Events announce results.

This separation keeps the Runtime predictable, extensible and loosely coupled.

---

# Responsibilities

The Event Model is responsible for:

- notifying Runtime components
- synchronizing Runtime state
- supporting background processing
- enabling extension interoperability
- triggering asynchronous work
- preserving Runtime consistency

Events never contain business logic.

---

# Event Lifecycle

Every Runtime action follows the same lifecycle.

```text
Command

↓

Runtime Service

↓

Validation

↓

Transaction

↓

Persistence

↓

Event Publication

↓

Subscribers
```

Events are published only after a successful transaction.

---

# Event Characteristics

Events are:

- immutable
- descriptive
- timestamped
- uniquely identified
- ordered within a transaction

Once published, an Event never changes.

# Event Consumers

Events may be consumed by:

- System Tools
- User Tools
- Runtime Services
- Job Runtime
- Companion
- Journeyman
- MCP
- future Extensions

Consumers never modify Events.

---

# Event Payload

Every Event contains:

- Event ID
- Event Type
- Timestamp
- Runtime Context
- Origin Service
- Affected Objects
- Metadata

Payloads should remain compact.

Large data should be queried through Runtime Services.

---

# Context

Every Event includes the Runtime Context that existed when the Event was created.

Later Context changes never modify historical Events.

This guarantees reproducibility.

---

# Ordering

Events generated by one transaction preserve their execution order.

The Runtime guarantees deterministic ordering inside a transaction.

Different independent transactions may execute concurrently.

---

# Event Processing

Subscribers react independently.

One failing subscriber must never prevent other subscribers from receiving the Event.

Errors are isolated and reported separately.

---

# Idempotency

Subscribers should safely process the same Event more than once.

Duplicate Event delivery must never corrupt Runtime state.

---

# Persistence

Events are transient Runtime messages.

They are not the permanent source of truth.

Persistent history belongs to:

- Projects
- Objects
- Knowledge
- Resources

Events describe what happened.

They do not become the history themselves.

---

# Long Running Work

Some Events create Jobs instead of performing work immediately.

Example:

KnowledgeCreated

↓

Knowledge Processor Job

↓

Analysis Job

↓

Relationship Discovery

The Runtime remains responsive while background work continues.

---

# Extensibility

New Extensions may publish and subscribe to Events.

Every Event must:

- describe something that already happened
- remain immutable
- remain independent from consumers

---

# Design Goal

Events should allow Cosmos to grow into a highly connected ecosystem without creating direct dependencies between components.

Every Runtime component should be able to react to changes while remaining completely independent from the implementation of other components.

---

# Principles

- Commands request work.
- Services perform work.
- Events announce results.
- Events are immutable.
- Events contain Context.
- Events never contain business logic.
- Subscribers remain independent.
- One failing subscriber never stops the Runtime.
- Events support unlimited extensibility.
